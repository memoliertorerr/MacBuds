# MacBuds — Standing Instructions

> Addressed to whoever is doing the work in this repo, whichever assistant that is.
> The build plan and its progress tracker live in `docs/BUILD_PLAN.md` — read it before any work.

## What this is

A native macOS controller for Samsung **Galaxy Buds2** (SM-R177). The owner no longer has an
Android phone, so this is the only way to change the earbuds' settings. It talks to the buds
over Bluetooth classic RFCOMM using Samsung's serial protocol, the same one the Galaxy Wearable
app uses.

Developed and tested on macOS 26, Apple Silicon, Xcode 26 / Swift 6.3. The earbuds are found
automatically among the Mac's paired devices by name (`BudsTransport.findEarbuds`); `--address`
or `MACBUDS_ADDRESS` picks one when several pairs are paired. Never hard-code an address.

## Stack and structure

One Swift package, four targets. Keep the layering strict — it is what makes the protocol
testable without hardware.

| Target | Kind | Depends on | Holds |
|---|---|---|---|
| `BudsProtocol` | library | Foundation only | Framing, CRC16, message IDs, payload encode/decode. **No IOBluetooth import, ever.** |
| `BudsTransport` | library | `BudsProtocol`, IOBluetooth | Device discovery, RFCOMM channel, `BudsSession` (request/response, state stream) |
| `macbuds` | executable | `BudsTransport` | CLI. Every feature lands here first. |
| `MacBudsApp` | executable | `BudsTransport` | SwiftUI `MenuBarExtra` app, bundled into `MacBuds.app` by `scripts/bundle.sh` |

In the app, `BudsViewModel` is the only thing that touches `BudsSession`. Views bind to
`model.state` and change settings with `model.apply { try .someCommand(...) }` using the
`Command` factories — never by building frames. The app holds the control channel for as long
as it runs, so quit it before using the CLI.

```
Package.swift
Sources/BudsProtocol/   Sources/BudsTransport/   Sources/macbuds/   Sources/MacBudsApp/
Tests/BudsProtocolTests/
scripts/macbuds-bundled.sh   run the CLI inside a minimal .app (required for Bluetooth access)
scripts/bundle.sh [--open|--install]   builds dist/MacBuds.app (release, ad-hoc signed)
README.md                    user-facing; keep its command table in step with `macbuds --help`
docs/BUILD_PLAN.md      docs/PROTOCOL.md      docs/captures/   raw frames from the real buds
docs/images/             README screenshots, generated by `MacBudsApp --render-screenshots docs/images`
LICENSE                  MIT
```

**Running the CLI against the buds:** always `scripts/macbuds-bundled.sh <args>`, e.g.
`scripts/macbuds-bundled.sh probe --channel 27`. The bare `.build/debug/macbuds` binary is
killed by macOS (exit 134, no output) when launched from an app without a Bluetooth usage
string, which includes agent sessions.

The control channel is the SDP service `GEARMANAGER`
(`2E73A4AD-332D-41FC-90E2-16BEF06523F2`), **not** the generic SPP UUID `0x1101`.

## Git — this project overrides the owner's global rule

The owner's global instructions say "never run `git commit` or `git push`". **For this
repository the owner has explicitly authorised the agent to run git itself** — `init`,
`commit`, `merge`, `push` and the like (granted 2026-11-10). So:

- After a step's verify is green, commit and push it yourself. One step = one commit.
- **No AI attribution** in commits or PRs: no `Co-Authored-By`, no "Generated with", no model
  or assistant names, no session links.
- Before anything that could discard uncommitted work (`checkout`, `restore`, `reset`,
  `clean`, `rm -rf`), run `git status` first and say what would be lost.
- After a broad `git add`, check `git status` and look at anything that could carry secrets.
- Never force-push. Never rewrite pushed history.
- The repository is public and MIT-licensed. Never commit a real Bluetooth address, serial
  number, or local filesystem path — use placeholders such as `<earbuds-address>`.
- `.claude/settings.local.json` is machine-local and stays untracked.

## Non-negotiable rules

1. **Never send firmware-update (FOTA) messages.** A bad flash can brick the earbuds and there
   is no recovery path without Samsung service. Not in code, not in experiments.
2. **Never send factory reset, or any message ID whose meaning isn't written down in
   `docs/PROTOCOL.md`.** No fuzzing or ID-scanning against the real device. If a message isn't
   documented, document it from a reference first, then send it.
3. **Reference, don't copy.** `GalaxyBudsClient` (github.com/timschneeb/GalaxyBudsClient) is
   GPL-3.0. Use it to learn protocol facts — IDs, payload layouts, constants — and record those
   in `docs/PROTOCOL.md`. Write the Swift from that document. Do not port or paste its code.
4. **CLI first.** A feature is implemented and proven in `macbuds` before it gets UI.
5. **Say what you could not verify.** The agent can run the CLI against the connected buds and
   read values back. It cannot hear, feel, or see the earbuds. Audible and physical effects are
   the owner's check — name them explicitly and say what to listen or look for.

## Conventions

- `BudsSession.send` only transmits IDs in `MessageID.sendable`. Adding an ID there is the
  deliberate act of declaring it safe — it must already have a host→buds row in
  `docs/PROTOCOL.md` §4, and never be anything from §5.

- Swift 6 language mode, strict concurrency. No `@unchecked Sendable` without a comment
  explaining why it is safe.
- `BudsProtocol` types are value types; decoding is `throws`, never crashes on malformed input.
- Byte layouts are documented in `docs/PROTOCOL.md` first, code second; tests use real captured
  frames wherever one exists.
- Docs in `docs/` as `.md`. After every change, update whatever went stale — this file,
  `docs/PROTOCOL.md`, and the tracker in `docs/BUILD_PLAN.md`.
- Ask when genuinely unsure. Flag useful follow-ups rather than silently doing them.
